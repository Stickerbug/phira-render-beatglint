# 性能对比与后续优化边界

本文只记录目前有证据的数据，并把未测量的方向单独列出。数值来自
2026-10-27 的历史 smoke 记录（提交 `c61711c`、`b267838` 及其绑定的
渲染器提交），不是本次发布后重新跑出的全量基准。公开仓库不包含输入
谱面、资源包或旧输出；因此读者不能直接复现下面的具体 SHA，只能按文末
方法在自己的输入上重测。

## 已测量结果

历史测试使用 Linux Xorg/Mesa、隔离 Rust 1.99.1 工具链、headless profile、
Credits 前缀输入（输入 SHA-256：
`59bad2003abb894bc7d2b2267f4c0282f213de5dae3ce1ee6d5d64c9cf6bc4ef`）、
320×180、10 fps 和 scene-time `[3.5, 4.0)` 的 5 帧窗口。

| 项目 | 对照 | 结果 | 能说明什么 | 不能说明什么 |
|---|---|---:|---|---|
| 构建 profile | `release` 0.767 s；`release-fast` 0.513 s | 约减少 33.1% elapsed，约 1.50× | 这个固定小窗口在该机器上受益于 `opt-level=3`、thin LTO 和单 codegen unit；两种构建的输出 SHA 相同（`cd16df306ad0ff7a5f978a539038063104b57cd70ccba469e5c58d6f6fc2edb0`） | 不能外推到整曲、其他 GPU/驱动、其他分辨率，也不能证明视觉 parity；`release-fast` 仍是显式对照 profile |
| 全路径音频混音 | 整曲缓冲改为 8192-frame 分块 | 解码后的共同 PCM 为 873,310 个 stereo samples；平均差 0，最大差 0，完全一致 | 分块没有改变该 Credits smoke 的混音结果，并限制了混音工作集 | 没有受控的旧/新耗时实验，不能宣称音频混音变快；RSS 同时受 GL、编码和运行时影响 |
| 三重 PBO 读回 | 修复尾部 drain，并复用 bounded RGBA 缓冲区 | 首部/尾部帧丢失问题得到修复；bounded 路径不再每帧重新分配 RGBA 缓冲区 | 这是输出正确性和分配行为的改进 | 当前没有稳定的 GPU/端到端耗时基准，不能写成“提升了多少百分比” |

音频记录中还出现过约 177,332 KiB 和 178,224 KiB 的 child max RSS，分别
对应不同代码状态；它们不是严格控制变量的 A/B 测试，不能据此宣称固定的
内存下降。历史记录中的一次完整 smoke 耗时约 1.27 s，PBO drain 后另一次
约 1.60 s；代码状态和输出路径同时变化，不能用来判断 PBO 或分块混音的速度
收益。

这些测试没有证明完整 Phira 的视频背景、全部粒子、命中特效、游戏音效、
随机 seek 或真人可玩性。当前 bounded profile 仍从时间零开始重放。

## 仍然值得测量的优化

1. **长曲音频事件索引。** 当前 full mixer 在每个 8192-frame chunk 内仍会
   重复检查谱面的音符。可以先按时间排序并维护 chunk 事件游标，减少长曲和
   高密度谱面的重复扫描。必须用 Credits 和较长的《詩超絆》各跑冷启动、
   热启动多次，并检查 decoded PCM 的逐样本一致性。
2. **resident worker 或 checkpoint。** bounded 窗口现在要从时间零更新和渲染
   到目标位置，窗口越靠后，前置成本越高。常驻进程或安全 checkpoint 可能是
   最大的批量预览收益，但必须定义并验证判定状态、粒子、特效、场景、视频和
   音频时钟的恢复协议；直接给 `TimeManager` 赋目标时间不能替代它。
3. **GPU 读回与编码流水线。** 可以在记录 GPU timer、CPU 等待时间和 FFmpeg
   管道阻塞后，单独比较 fence、持久映射、双缓冲和编码进程并行。驱动兼容性
   和帧序必须先通过逐帧 hash 检查。
4. **短片段音频写入。** `music-only` 路径可以把小块样本合并成较大的交错
   缓冲再写入临时文件，减少 `write_all` 调用；这属于低风险 I/O 优化，仍需
   检查 AAC 时长和首帧时钟。
5. **编码 profile。** 可以单独提供质量、文件大小和速度都有明确记录的
   FFmpeg preset 或硬件编码 profile，但不能把编码速度换成默认视觉质量承诺。
6. **单帧 PNG 路径。** 若测得 FFmpeg 启动占据单帧耗时的大部分，可以比较
   直接 PNG 编码；输出像素必须与当前 readback 对齐，不能牺牲颜色和 alpha。

## 测量规则

下一轮性能改动应固定输入包、皮肤、分辨率、fps、scene-time 窗口、渲染器
提交和二进制 SHA；冷启动和热启动分开记录，至少重复 5 次并报告中位数和
范围。每次还应保存：elapsed、child max RSS、CPU 时间、GPU 等待时间（若可
得）、ffprobe 流信息、逐帧 hash，以及有音频时的解码 PCM SHA。任何改变
分辨率、fps、编码 preset 或输出质量的实验都要单独分组。

在获得这些数据之前，项目不会宣称“全曲加速”“任意机器加速”或“与官谱
完全一致”。

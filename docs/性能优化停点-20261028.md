# 性能优化停点

本文记录当前渲染架构的实测停点。数字来自本机 Linux Xorg/Mesa，不能外推到其他 GPU、驱动或完整音视频生产渲染。

## 当前结论

resident 顺序窗口已经是预览主模式的合适实现：一次加载场景和 GL context，按时间从零回放，把选中的帧写入多个输出。它解决的是重复启动和重复回放，不是把同一场景拆成多个线程。完整路径仍保留，用于最终音频、视频背景和完整 Phira 视觉复核。

同一首谱面不能安全地并行更新多个 `GameScene`：场景、时间管理器、粒子/特效状态和 GL context 都是可变的线程局部对象，不能跨线程共享。为每个窗口启动一个进程又会重复从零回放，并在软件 Mesa 上争用 CPU/GL，通常抵消 resident 的收益。不同歌曲或互不依赖的任务可以由外部调度器并行。

## 已测数据

| 测试 | 结果 | 说明 |
|---|---:|---|
| 1920×1080，30 fps，40.3–42.3 s 片段，软件 Mesa | 总回放 69.318 s | 为得到 2 s 输出，场景仍从 0 s 回放到 42.3 s，共 1270 个循环帧 |
| 上述 1080p30 profile：`update_render` | 61.192 s（88.3%） | 当前最大成本，属于 Phira 场景更新和绘制 |
| 上述 profile：读回写入/GL 读回/管道写入 | 4.964 / 2.201 / 0.959 s | 合计约 8.1%，不是当前第一瓶颈 |
| 上述 profile：FFmpeg 等待 | 1.130 s | 约 1.6% |
| resident，Credits，320×180，30 fps，两个连续窗口 | 2.465 → 1.206 s | 一次回放减少约 51.1%，两个窗口逐帧 SHA-256 与独立输出相同 |
| 1080p60 RGBA 与 RGB24 A/B | 22.17 s → 57.61 s | RGB24 虽减少字节数，却明显更慢，已撤回该改动 |

其他已完成的低风险优化包括复用 bounded RGBA 缓冲、完整 drain 三重 PBO、分块音频混音、缓存音符事件帧位置，以及视频追帧时只复制最终解码帧。这些改动已经覆盖分配、尾帧完整性和无效 CPU 拷贝等可验证问题。

## 暂不继续的方向

- 不在同一谱面内部加入线程池或多个 GL worker；目前没有安全的状态快照/恢复协议。
- 不把 bounded 读回改成 RGB24；现有 1080p60 A/B 已否定该方向。
- 不用异步写线程掩盖 GL 读回。当前管道写入占比很小，额外复制会增加内存和带宽；只有出现明显管道阻塞时才重新评估。
- 不删除完整渲染路径。resident 是预览优化，不具备完整音频、视频背景和跨随机特效状态的生产保证。

## 何时重新测量

只有出现以下变化之一时才重新做性能 A/B：

1. 更换 GPU/驱动、渲染后端、分辨率（尤其 1920×1080 或更高）或目标帧率；
2. 修改 `GameScene`、粒子/视频更新、MSAA、纹理上传或 GL readback；
3. profile 显示 `readback_gl_s` 或 `readback_io_s` 超过总循环时间的 15%，或 FFmpeg 等待超过 25%；
4. 出现可复现的多歌曲批处理需求，此时测试外部任务级并行，而不是场景内线程化。

每次复测必须同时记录分辨率、fps、窗口范围、GPU/驱动、`frame_loop_s`、`update_render_s`、读回分项、编码等待、输出帧数和像素/音频校验结果。没有这些数据，不接受“优化有效”的结论。
